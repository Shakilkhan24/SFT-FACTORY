# Gate G1 — evidence

Every row of checklist 03's **GATE ROWS — G1, Phase-0 exit** table, with the evidence that
ticks it. A row is ticked only when the evidence is *attached*, not when the work is "believed
done".

Status key: ✅ ticked · 🟡 partly ticked, with the gap named · 🔒 owner-only row · ⏸ blocked

**How to read the verify commands.** Several rows in the checklist name a command that does
not match where the proof actually lives — the checklist was written before the suites were
filed. This pack records the command that **was** run, and, where it differs, says so. Every
correction is a *route* correction: the assertion the row asks for is proved, but not at the
path the checklist names. No row's substance is waived anywhere in this pack.

**Environment.** All outputs below were captured on the dev cluster from
`docker-compose.dev.yml` (`postgres:16-alpine`, the same major version the pack validated
against), against a migrated database `factory_g1_doctor`.

## CL-G1-04 · A0.4 two runs of the same trivial task resolve an identical context

**✅ Ticked.** Verify: `pnpm exec vitest run tests/unit/orchestrator-a0-4-identical-context.test.ts`
→ 7 passed.

```
$ pnpm exec vitest run tests/unit/orchestrator-a0-4-identical-context.test.ts
 ✓ tests/unit/orchestrator-a0-4-identical-context.test.ts (7 tests) 22ms

 Test Files  1 passed (1)
      Tests  7 passed (7)
```

**Route correction.** The checklist names `… -t "A0.4"`, which would run `tests/acceptance/`.
The A0.4 oracle was **missing** when this pack was written — the only `A0.4` in the repository
was a mislabelled test in `tests/unit/deps-rule-negative.test.ts` that belongs to a
*different* list (the dependency rules). The oracle was **built** here, as
`tests/unit/orchestrator-a0-4-identical-context.test.ts`.

**What the suite proves.** Two runs of the same trivial task resolve the **same** context
manifest — compared field for field: the `resolvedContextSha256`, the `envelopeId`, the
`items` and the `gaps`. The **whole run** is compared too, not only the context: the same
artefact digest, the same node list, the same cost. A test that compared only the context
would pass even if the rest of the run were non-deterministic.

**The record is read from the object store**, as the bytes that were written, and parsed. It
is **not** read from the run's return value — and that distinction is the whole point. See
the next section.

**The guard on the guard.** The first version of this test compared `outcome.record`. The
run's outcome carries `recordUri` and `recordSha256` — **not** the record — so `outcome.record`
is `undefined`, and `expect(two.record?.context).toEqual(one.record?.context)` was
`toEqual(undefined, undefined)`: it passed against a build whose context resolution was
**random**.

The test now reads the bytes, and it asserts that a context **is present**:

```ts
expect(record.context).toBeDefined();
expect(record.context.resolvedContextSha256).toBe(CONTEXT.manifest.resolvedContextSha256);
```

Without that, every comparison above could pass on `undefined`.

**The mutation is in the harness.** `pnpm run test:mutation:orchestrator` now carries *"the
resolved context digest becomes random"*, which makes the resolved digest a fresh random
value on every run. It is **caught** — 3 of the 7 tests fail:

```
$ pnpm run test:mutation:orchestrator
…
CAUGHT   the resolved context digest becomes random

28 caught, 0 survived, 0 vacuous
```

**Why the determinism is injected, not hoped for.** The clock is a **fixed** instant and the
id generator is a **counter**, so the two runs differ in nothing but the run's own identity.
If the run read the wall clock, or generated a random id, two runs would differ for reasons
that have nothing to do with the context resolution — and the test would be measuring the
clock.

**A note on scope.** checklist 04 §"the context envelope" names this property directly —
*"Same inputs ⇒ same envelope (golden-file tests; A0.4, A1.10)"* — and the context
**assembler** itself is checklist 04's build (T-2.01). What is proved here is the property on
the `H.hello` workflow's context, which is the trivial task the gate row names. The
assembler's own golden-file test lands with the assembler.

## CL-G1-06 · A0.6 every projection can be dropped and rebuilt identically

**✅ Ticked.** Verify: `pnpm exec vitest run tests/unit/projections-a0-6.test.ts` → 9 passed (in
the output above); and `factory projections rebuild` against the real database.

**Route correction.** The checklist names `… -t "A0.6"` (which routes to the acceptance
directory) and `factory projections rebuild`. The suite is in `tests/unit/`.

**What the suite proves.** Each projection is a **pure reducer** over the event log: drop the
table, replay the log, and the rebuilt table is byte-identical to the dropped one.

The exit criteria name the comparison method — *"reproduces identical rows (hash compare)"* —
and the suite does **both**: a **digest** of each projection's rows before and after, and a
**field-for-field** comparison. The digest says "these differ"; the operator needs "this row
differs in this field". So the rebuild's report carries `beforeDigest`, `afterDigest` and a
`differences` list per projection, and the assertion is that the list is **empty**:

```
expect(report.identical).toBe(true);
expect(rowsDigest(await store.read('task_current'))).toBe(before.task_current);
expect(rowsDigest(await store.read('approval_queue'))).toBe(before.approval_queue);
expect(rowsDigest(await store.read('cost_attribution'))).toBe(before.cost_attribution);
for (const comparison of report.comparisons) {
  expect(comparison.differences).toHaveLength(0);
  expect(comparison.beforeDigest).toBe(comparison.afterDigest);
}
```

**The rebuild is not a no-op.** A second proof asserts that the rebuild actually **dropped
and replayed** — a rebuild that replayed nothing would also report "identical", and would
pass the hash compare for the wrong reason. The suite checks that the projection rows carry
the log's own content rather than a stamp the rebuild wrote.

The command itself is exercised against the real database in
`tests/unit/projections-cli.test.ts` — including that `rebuild` **demands `--yes`** before it
drops anything, and that the safe form (`catch-up`, `status`, `check`) does not.

## CL-G1-12 · Event hash chain verifies on the hello-task run

**✅ Ticked.** Verify: `factory audit chain tsk_hello_g1_0001` → **exit 0**.

```
$ export FACTORY_PROJECTOR_DATABASE_URL="postgresql://factory:factory@127.0.0.1:5432/factory_g1_doctor"
$ node apps/cli/dist/bin.js audit chain tsk_hello_g1_0001
chain: intact (6 links checked)
  aggregate: task:tsk_hello_g1_0001
  links:     6
$ echo $?
0
```

**What was verified.** A **real** `H.hello` run — `FakeProvider → artefact → record`, driven by
`tools/hello-run.ts` — wrote six events to the real `factory.events` table, and the CLI
verified their hash chain against the real log.

**The tamper, for the other half of the oracle.** The row's stored hash was altered the way an
editor with database rights would do it: as the owner, with the append-only trigger disabled.
The command then reported:

```
chain: BROKEN at seq 3
  aggregate: task:tsk_hello_g1_0001
  links:     6
  reason:    hash mismatch at seq 3
$ echo $?
1
```

And an aggregate with **no events** reported:

```
chain: NOTHING TO VERIFY
  aggregate: task:task-with-no-events
  links:     0
  reason:    the aggregate has no events, so there was no chain to verify
$ echo $?
1
```

**A defect this row found, and the fix.** The first version of `PostgresChainVerifier` read
the count from a field the contract did not carry and fell back to `0`, so the command printed
**"chain: intact (0 links checked)"** while the log held six events — a pass on nothing. The
count could not be added to `ChainVerification` (it is `.strict()` in `@factory/contracts`, and
HR-12 forbids changing it), so `PostgresEventLog` grew a **separate** method,
`verifyChainDetailed`, that carries `checked` and `reason`; `verifyChain` keeps the exact
contract shape. The CLI also now treats an **empty** chain as a failure, because "there was
nothing to verify" is not "the history was verified".

**Route correction.** The checklist names `factory audit chain <taskId>`. The command is now
runnable — T-1.17 added the missing `factory` binary — but it is invoked as
`node apps/cli/dist/bin.js audit chain <taskId>` unless `apps/cli` is linked onto the `PATH`.
It reads the log through the **projector** role, so `FACTORY_PROJECTOR_DATABASE_URL` (or
`FACTORY_OWNER_DATABASE_URL`) must be set. The exit codes are **0** for intact and **1** for
broken — deliberately not 2, which is the CLI's "you invoked me wrongly".
