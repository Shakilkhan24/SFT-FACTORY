# T-1.14 · Access-point API and auth — the R4 boundaries

## What this ticket delivered

`apps/api` — the factory's own HTTP API, the **only** way humans enter the
control plane. The routes are real: real authentication, real
`application/problem+json`, real idempotency, real rate limiting, real
event emission. The **domain behaviour** behind each route is a port with an
in-memory double.

Six access points (blueprint `13` §3.1), each with its declared authority:

| Access point | Routes |
|---|---|
| AP-1 `define-intent` | `POST /v1/intents` |
| AP-2 `approve` | `GET /v1/approvals`, `GET /v1/approvals/{id}`, `POST /v1/approvals/{id}/decision`, `POST /v1/approvals/{id}/revoke` |
| AP-3 `review` | `GET /v1/reviews`, `GET /v1/reviews/{taskId}`, `POST /v1/reviews/{taskId}/decision` |
| AP-4 `inspect` | `GET /v1/views/overview`, `GET /v1/tasks`, `GET /v1/tasks/{id}`, `GET /v1/tasks/{id}/events`, `GET /v1/tasks/{id}/runs`, `GET /v1/runs/{id}`, `GET /v1/runs/{id}/artefacts/{name}`, `GET /v1/metrics/summary`, `GET /v1/audit/explain`, `GET /v1/stream` |
| AP-5 `intervene` | `POST /v1/tasks/{id}/{pause\|resume\|cancel\|escalate\|rerun}`, `POST /v1/factory/kill-switch`, `POST /v1/grants/temporary`, `POST /v1/tasks/{id}/defect-flag` |
| AP-6 `amend-factory` | `GET /v1/definition/plan`, `POST /v1/definition/apply` |
| — | `POST /webhooks/github`, `GET /healthz`, `GET /readyz`, `GET /metrics` |

Thirty-two routes, and the app registers **from the inventory** — so there is
no second place a route could be added, and the inventory test covers every
route the server actually serves.

## The four boundaries this ticket did **not** cross

Each of these is a port with an in-memory double. They are recorded here, not
silently dropped, because each one is another ticket's work.

### 1. `packages/approvals` and `packages/review` — R4, not named by the ticket

HR-5 says touch only the ticket's `Build` paths, and the ticket names
`apps/api`. The approval and review **domain** logic — what an approval
state machine permits, when a review may be deferred — lives in those
packages and is not this ticket's to build.

So `apps/api/src/ports.ts` declares the ports, and `apps/api/src/fakes.ts`
ships the doubles. What the API *does* own, and does own fully, is the
**access-point contract**: the approver list, the hash binding, the expiry,
the required rationale, the event per decision.

**What the owner needs to decide:** whether the approval and review packages
land in T-1.15's scope, in a later checklist, or as a separate stream. The
API is already shaped for whichever it is — the port is the seam.

### 2. The GitHub webhook's signature verification — pack `04` §4 is not opened

The ticket says "Open ONLY" pack `04` §3. The webhook's HMAC verification
lives in pack `04` §4 and in `packages/scm-github`, which is T-1.09's
package and does not yet ship the adapter.

So `POST /webhooks/github` **refuses** with `501`, naming the gap. It does
not accept a delivery and pretend it verified one, and it does not record an
intent from an unauthenticated payload — a refused delivery changed nothing,
so it leaves no event behind.

### 3. The SSE stream — T-1.15's projections

`GET /v1/stream` (pack `04` §3, AP-4) is SSE with `task.updated`,
`approval.requested`, `review.queued`, `health.changed`, `cost.updated`,
`killswitch.changed`, and `id:` = the event's `seq` for `Last-Event-ID`
resume.

The stream's **source** is the event log, and the projections that turn the
log into the stream's event classes are **T-1.15**. So the route exists and
is authenticated — a stream nobody can reach would be worse than one that
says so — but it refuses with `501`.

It refuses with `501`, not `200` with an empty body: a client that connects
and sees nothing cannot tell "no events yet" from "not implemented", and the
second must not look like the first.

### 4. The Postgres-backed reads — R4 `migrations/**`

The reads that answer `/v1/tasks` and `/v1/runs` come from the projections,
which are T-1.15. The read port is injected and the double answers.

## The two defects this ticket's own tests found

Both were design errors, not typos, and both are now covered by tests that
**fail** when the rule is broken.

### The idempotency conflict check was dead code

`recordId` hashed `(login, method, path, key)`. So a key reused on a
*different* route produced a different lookup id — the store **missed**,
`sameRoute` was unreachable, and the caller got **two actions from one key**.

That is the exact failure the idempotency mechanism exists to prevent: one
human click, one flaky connection, one intent — but two runs of a workflow,
which spends money, opens a pull request, and can merge something.

The fix: the lookup identity is `(login, key)` and the route is compared
**after** the lookup. A hit on a different route is a `conflict` — the
caller made a mistake — rather than a silent second action.

### The health check answered `429`

A rate-limited health check tells the orchestrator the process is down when
it is merely busy. That false negative can trigger a restart loop, which is
worse than the load the limit was there to shed.

The fix: the exemption is **declared in the inventory** (`rateLimited: false`
on `/healthz` and `/readyz`), and the app treats the flag as *opt-out* — an
absent flag means the route **is** rate-limited, so a new route cannot be
unbounded by omission.

The first attempt at this fix read the optional flag as truthy-only, which
silently made every route unbounded. The mutation harness caught it.

## The one design change the mutation harness forced

The rule "a refused call records no event" was implemented **six times** —
once per handler, each checking its own port result and returning early. So
`emitFor`'s own refusal branch was **unreachable**, and no test could
observe it.

That is the T-1.11 / T-1.12 lesson exactly: a check that cannot be observed
is not a check.

So the handlers now hand the **port's own outcome** to `emitFor`, and
`emitFor` alone decides what a refusal means. One rule, one implementation,
and a handler cannot opt out of it. `emitFor` takes a `PortResult` (success
or refusal, no HTTP status) and a `status` argument, so the port does not
have to know HTTP and the handler does not have to guess it.

## The known environment limits (not regressions)

- **No Docker daemon** ⇒ the Postgres-backed suites *skip*.
- **`tests/unit/baseline.test.ts` A0.32/A0.33 fail on a clean tree** — the
  baseline tool writes to `/tmp`, which this WSL environment cannot create
  in. Proved on T-1.10, T-1.11, T-1.12 and T-1.13.
