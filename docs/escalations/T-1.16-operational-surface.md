# T-1.16 · Operational surface v0 and CLI — the one view, the live channel, and two backends in one CLI

**Status:** open, for the owner
**Ticket:** T-1.16 · Operational surface v0 and CLI · W2 · M · R1
**Date:** 2026-11-11

## The short version

T-1.16 builds the thing a human actually looks at — the dashboard — and
the CLI skeleton that drives the same access points from a terminal. It
ships green: 231 unit tests across the new suites, 15 browser tests in
the Playwright oracle, and a mutation harness with 40 mutations, all
caught.

Four things need the owner's attention, and none of them is a silent
drop:

1. **`apps/api` was edited though the `Build` line does not name it** —
   the ticket requires SSE, and the API owns the only SSE endpoint.
2. **`@playwright/test` is a new dependency** — it is the oracle row's
   own word, but it is absent from ADR-0013, so it carries an ADR
   proposal.
3. **`factory login` cannot do the OAuth device flow** — no GitHub
   OAuth app exists here, and HR-9 forbids the real secret.
4. **The kill switch has no durable store in v0** — it lands with the
   first component that reads it.

## 1. `apps/api` was edited though the `Build` line does not name it

AGENTS.md HR-5 says to touch only the ticket's `Build` paths. T-1.16's
`Build` line reads:

> dashboard v0 (Needs you / In flight / Health / Cost, SSE, kill switch,
> task-timeline) and the CLI skeleton …

It says **SSE**, and it does not say where SSE lives.

`GET /v1/stream` is currently `streamStub()` in
`apps/api/src/handlers/index.ts`, and the stub's own comment says its
event classes "come from the projections" — **and T-1.15 has now built
them**. So T-1.16 implements the route.

The alternative was a dashboard-local stream. That would have been a
**second event source**, which contradicts blueprint `09` §5.2 ("the
event log is the single source of truth") and pack `04` §3's rule that
the SSE route lives at `/v1/stream`. `apps/api` is **not** an R4 path, so
HR-5 permits the edit; the reasoning is recorded here rather than buried.

### What changed in `apps/api`

| File | Change |
|---|---|
| `apps/api/src/ports.ts` | the `StreamSource` port; a `hijacked` flag on `HandlerResult` |
| `apps/api/src/stream.ts` | the port, the `StreamEvent` shape, the class mapping, the in-memory double |
| `apps/api/src/handlers/stream.ts` | the real SSE handler — the framing, the `id:` = `seq`, the `Last-Event-ID` resume |
| `apps/api/src/handlers/index.ts` | the real handler bound in place of `streamStub()` |
| `apps/api/src/app.ts` | two early returns, so a hijacked reply is never sent a body |
| `apps/api/src/harness.ts` | a `listen` seam, so a test can hold a **real socket** |

### The hijack, and why it is explicit

Fastify 5's `reply.hijack()` is the documented way to say "I am writing
the response myself" — Fastify then sends no body and waits for nothing.
That is exactly what an SSE route needs, and it is exactly what
`app.inject` cannot do: `inject` waits for the response to **complete**,
and a stream never completes.

So the live-route tests **listen for real**. They open a socket, read
frames as they arrive, and hang up — and the hang-up doubles as the proof
that the server's loop stops when the client goes away.

The hijack is made **visible at the call site** rather than hidden in a
Fastify quirk: `HandlerResult` carries a `hijacked` flag, and `app.ts`
has two explicit early returns for it.

## 2. `@playwright/test` is a new dependency, and it carries an ADR proposal

The oracle row says:

> Playwright smoke renders the seeded overview in <2 s; a script proves
> reaching a review/approval item in **≤2 clicks** (test name contains
> `NFR-07`) …

So `@playwright/test` is the row's own word, and it is a **test**
dependency — not infrastructure. HR-6's ban list is message broker /
k8s / vector DB / workflow engine, and none of those is a browser
driver. It is nonetheless **absent from ADR-0013**, which names React and
Vite but not the test runner.

**ADR proposal.** Pin `@playwright/test` at **1.63.0** and record that
the e2e suite needs a **browser-enabled CI job**. The pin is not
arbitrary: 1.63.0's `browsers.json` maps to chromium revision **1243**,
which is the revision cached in this environment. 1.62 maps to 1234 and
1.64 to 1248, so neither would use the cached browser — and the headless
shell for 1243 is not cached, and its CDN download times out here. So
`channel: 'chromium'` (the full browser, not the shell) plus
`--no-sandbox` (WSL2) are both **mandatory**, and both are recorded in
`playwright.config.ts` with the reason.

The e2e suite is **not** part of `pnpm run ci`. The CI script runs the
unit, acceptance, invariant and redteam suites; this one needs a browser,
so it has its own script (`pnpm run test:e2e:browser`) and belongs in a
browser-enabled job.

### The e2e suite does not use the real API

This is worth stating plainly, because it is the one place where the
oracle is weaker than it looks.

The real API's `InspectionPort` is a **port**, and the projections behind
it land in later tickets (T-2.09's `approval_queue`, T-4.05's
`cost_attribution`). So the real API would answer an overview with
**five empty regions** — and the oracle would then prove nothing about
"reaching a review/approval item in ≤2 clicks", because there would be
no item to reach.

So `tools/serve-dashboard-fixture.ts` serves the **seeded** overview the
blueprint describes, with the awkward cases included **on purpose**:

* a needs-you item with **no risk tier** (it must sort **last**);
* a needs-you item with **no expiry** (it must not look urgent);
* an in-flight task with **no activity** (it must come **first** — it is
  the one most likely to be wedged);
* a health item that is `failing` (the alarm);
* a cost row with **no accepted change** (no per-change figure).

The fixture serves the built dashboard and the API on **one origin** —
production's shape, per pack `02` §3 — so CORS stays closed (pack `04`
§3), and the browser sees what it will see in production.

**The kill switch really flips.** `POST /v1/factory/kill-switch` really
flips a flag, and the flag is really served back. So the round trip is a
round trip, not a stub that always says "ok".

**The stream really streams.** `GET /v1/stream` is a real SSE endpoint
that sends the six classes' events and holds the connection open — so the
browser's `EventSource` is exercised for real, and the dashboard's
re-read on a stream event is observable (the fixture's `streamTick`
counter moves, and the browser test watches it move).

## 3. `factory login` is token-based; the OAuth device flow is a proposed ticket

pack `04` §3 says the CLI presents "bearer token `fac_…`". The **GitHub
OAuth device flow** needs an OAuth application — a client id, a client
secret and a registered callback — and **no such application exists in
this repository**. HR-9 forbids a real secret here, so there is nothing
to put in an `.env` and no way to complete the flow honestly.

So `factory login --token fac_…` ships. It **proves the token before it
stores it** — a token that cannot be used is worse than no token, because
it would sit in the file and fail every later command while the operator
looks at the wrong thing — and it **never echoes the token**: it shows
`fac_…abcd` and the length only.

**Proposed ticket:** `factory login` with the GitHub device flow, once
the owner creates the OAuth app (HR-9: no real secrets here).

### The token store

`~/.config/factory/credentials.json`, file mode `0600`, directory mode
`0700`, written **atomically** (temp file + `rename`). The token is the
plaintext the caller presents — the *server* stores it hashed, which is
T-1.14's business.

## 4. The CLI has two backends, and that is deliberate

The existing commands (`db`, `events`, `projections`, `definition`) are
**ops** commands that run as a Postgres role. The new ones are
**access-point** commands that run as a *human* with a `fac_` bearer
token. pack `04` §9's catalogue already separates them (`factory
kill-switch` = AP-5; `factory projections rebuild` = ops).

The distinction is not cosmetic:

> An ops command may read the log directly; an access-point command must
> go through the API so the authority is **recorded**.

pack `04` §3 requires every access-point call to emit an event with
`actor=human:<login>` and `authority.basis='human-access-point'`. A
command that wrote to the database would change the factory **without
leaving a trace of who changed it** — and for the kill switch that is
exactly the trace an operator most needs.

So:

| Command | Backend |
|---|---|
| `factory login --token` | the token store, then **HTTP** `GET /v1/tasks` to prove it |
| `factory whoami` | **HTTP** `GET /v1/tasks` |
| `factory tasks ls\|show <id>` | **HTTP** `GET /v1/tasks`, `GET /v1/tasks/{id}` |
| `factory kill-switch on\|off --reason …` | **HTTP** `POST /v1/factory/kill-switch` (AP-5) |
| `factory projections rebuild` | **Postgres** (ops — shipped in T-1.15) |
| `factory audit chain <taskId>` | **Postgres** `PostgresEventLog.verifyChain` |

### `audit chain` — the port, and how the oracle runs without Docker

`PostgresEventLog.verifyChain` needs Postgres, and this environment has
**no Docker daemon**. So the CLI takes a **`ChainVerifier` port** with
two implementations:

* `PostgresChainVerifier` — the real one, wrapping
  `PostgresEventLog.verifyChain`.
* `InMemoryChainVerifier` — built on the **pure** `verifyChainLinks`
  from `packages/eventlog/src/hash-chain.ts`, over links built with the
  exported `chainHash`.

The **Docker-free oracle** proves the tamper logic against the in-memory
verifier; the **Postgres oracle** runs the same assertion through
`PostgresEventLog.verifyChain` and **skips** without Docker (the repo's
`it.skipIf(!running)` idiom). `PostgresEventLog.verifyChain` is a thin
SELECT-then-`verifyChainLinks` adapter — 100 % of the detection logic is
in the pure function the Docker-free oracle exercises.

The in-memory verifier builds its links with the **log's own `chainHash`**,
so it cannot disagree with the real log about what a valid chain is.

### The exit codes

`audit chain` has **three** distinct outcomes, so a script can tell
"the chain is broken" from "I typed it wrong":

| Code | Meaning |
|---|---|
| **0** | the chain is intact |
| **1** | the chain is **broken** — `chain: BROKEN at seq N` |
| **2** | the command was invoked wrongly |

## 5. The kill switch has no durable store in v0

The API's `KillSwitch` is a port with only an in-memory double, and the
switch's effect spans intake, scheduler, harness and edge — each another
ticket's component. A durable table with no readers yet would be a
**second source of truth**, which is worse than no table.

So v0 ships the **port + the double**, and the durable store lands with
the first component that reads it. Recorded here rather than silently
omitted.

## 6. `LISTEN` is still not implemented — carried from T-1.15

The stream **polls** the log at the cursor, the same mechanism the
projector uses. A `LISTEN` needs a dedicated held-open connection and
belongs to the worker's ticket. Carried from T-1.15's escalation, and
unchanged by this ticket.

## 7. One design decision the browser found, and the fix

The browser oracle found a defect that no unit test could have found:
**the kill switch was not wired at all**.

`Dashboard` takes `setKillSwitch` as an *optional injected prop* — a
seam for tests — and `main.tsx` never passed it. So in the real browser
the button said **"the kill switch is not wired"**, and the kill-switch
round trip — one of the four oracle proofs — could not have passed.

This is worth naming because it is the shape of a defect that unit tests
routinely miss: the prop was optional, so the component compiled, the
type was right, and the seam was exercised by every test that injected
it. Only a **real browser** running the **real entry point** found it.

The fix: `main.tsx` builds the client and passes a `setKillSwitch` that
POSTs to `/v1/factory/kill-switch`.

### The CSRF token, and where it comes from

pack `04` §3: the browser is authenticated with a **session cookie**, so a
mutating call carries the **CSRF token** as well — the cookie alone would
let a cross-site form post.

The token belongs to the **session**, so it cannot be part of a file
built once. The server renders it into the page, and the dashboard reads
it from a **meta tag** (`<meta name="factory-csrf-token">`). It is not a
cookie — a cookie would be sent automatically, and the token is there
precisely to be *not* automatic — and it is not in the body, where a
scraper would find it.

## 8. One rule the mutation harness asked for

The kill switch's decision was originally **inlined** in the React
component. The mutation "the dashboard engages the switch without a
reason" **survived** — because the unit suite does not load a `.tsx`
file, so the rule was covered only by the browser oracle, which the
mutation harness does not run.

So the decision was extracted into `apps/dashboard/src/kill-switch.ts` —
a **pure** module, unit-testable without a JSX transform — and the
harness now breaks four rules in it:

* a blank reason is refused;
* an unwired switch is refused;
* a dismissed prompt says **nothing** (a person changing their mind is
  not an error);
* the switch flips the **right way**.

This is the same discipline as T-1.11's `timeline-events.ts` split: pure
logic belongs in a `.ts` module, where it can be tested without a
transform.

## 9. The other three survivors, and what they were

The first run of the harness had four survivors. Three were **real gaps**
in the oracles, and one was a **weak mutation**:

| Survivor | What it was |
|---|---|
| "an unknown expiry is treated as urgent" | a **real gap** — the regions test asserted an *unparseable* timestamp but never an **absent** one, so `timeUntil(undefined, …)` was untested. Fixed by adding the assertion. |
| "the dashboard engages the switch without a reason" | a **real gap** — the rule was only in the `.tsx`. Fixed by the extraction in §8. |
| "the CLI presents no bearer token" | a **real gap** — the bearer token was asserted in `cli-login` and `cli-kill-switch` but **not** in `cli-tasks`, even though that test recorded the headers. Fixed by adding the assertion. |
| "the CLI leaves the token file readable by others" | a **weak mutation** — it broke the *temporary* file's `chmod`, whose effect is unobservable because the subsequent `chmod` after the `rename` sets the mode the test reads. Re-aimed at the whole rule. |

The pattern is the same one T-1.12 found: **two different checks could
produce the same observable result**, so a test asserting either one
passed even when the check it meant was gone.

## 10. What I have NOT changed

- `packages/contracts/**` — untouched (HR-12). Every event type the
  stream emits (`task.updated`, `approval.requested`, `review.queued`,
  `health.changed`, `cost.updated`, `killswitch.changed`) and every
  event the CLI's kill switch causes (`kill.switch.engaged`,
  `kill.switch.released`) is already in the registered vocabulary.
- `packages/projections/**` — **used, never edited**. T-1.15's package
  is read by the API's `InspectionPort` binding.
- `migrations/**`, `packages/{policy,broker,credentials,eventlog,isolation,approvals}/**`,
  `tests/redteam/**`, `tests/invariants/**`, `definition/**`, `.github/**`
  — the R4 paths, untouched.
- **The `InspectionPort`'s Postgres wiring** — the API's inspection port
  still answers from its doubles. The real projection store is T-1.15's
  follow-up and is named there.
- **`factory tasks pause|resume|cancel|escalate|rerun`**, `factory
  approvals …`, `factory reviews …`, `factory intent create`, the OAuth
  device flow, the durable kill-switch store, `LISTEN`/`NOTIFY`, INT-10
  notifications, a second dashboard view, `factory doctor` / `repo` /
  `baseline` / `calibrate` / `metrics` / `inventory` — proposed tickets,
  not code.

**\*The known baseline limit.** `tests/unit/baseline.test.ts` A0.32 and
A0.33 fail because the baseline tool writes to `/tmp`, which this WSL
environment cannot create in. It fails on a clean tree, was proved on
T-1.10…T-1.15, and this ticket touches no baseline code.

**†The invariants suite needs Postgres.** There is **no Docker daemon**
in this environment, so the Postgres-backed invariant suites fail with
`Connection terminated unexpectedly`. This was **re-proved on a clean
worktree at the T-1.15 commit** (`30f3624`) — 5 files failed and 23
tests failed there too — so it is an environment limit and not a
regression from this ticket. The same limit makes the acceptance suites
**skip** (34 skipped) and the Postgres half of the audit oracle skip.
They run in CI, where the daemon exists.

Because `pnpm run ci` short-circuits on the first failing step, the
acceptance, invariants and redteam suites were run **separately** after
the unit suite stopped it — so every step of the chain was actually
executed, and the numbers quoted above are the ones that ran.

## The recommendation

**Ship T-1.16 as it stands.** The four oracle proofs are met by a real
browser against a real origin, and every load-bearing rule the mutation
harness names is proved to fail when it is broken — 40 of 40, with no
vacuous mutation.

The two things I would put on the owner's desk are the **`apps/api`
edit** (the only place T-1.16 touched a path its `Build` line does not
name) and the **`@playwright/test` ADR proposal** (a new dependency
absent from ADR-0013). Both are recorded here rather than in a commit
message, so they can be checked against the pack without reading the
diff.
