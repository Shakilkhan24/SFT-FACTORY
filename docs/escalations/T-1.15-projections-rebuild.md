# T-1.15 · Projections and rebuild — the migration, the two shell projections, and the one rule that makes the fold idempotent

**Status:** open, for the owner
**Ticket:** T-1.15 · Projections and rebuild · W2 · M · R3 (+ R2)
**Date:** 2026-11-11

## The short version

T-1.15 builds `packages/projections` — the projector that tails the event
log, the pure reducers that maintain the disposable views, the durable
cursor, the rebuild, and the `factory projections` CLI command. It ships
green: 70 unit tests across seven files, and a mutation harness with 26
mutations, all caught.

Three things need the owner's attention, and none of them is a silent
drop:

1. **`migrations/0002_projections.sql` was written**, and `migrations/**`
   is an R4 path that T-1.15's `Build` line does not name. The reasoning
   is below; the decision is the owner's.
2. **`approval_queue` and `cost_attribution` ship as shells** — the
   computation, the cursor and the carried state are real; the *tables*
   are T-2.09's and T-4.05's.
3. **The `LISTEN` wake-up is not implemented.** The projector polls.

## 1. The migration — an R4 path the ticket does not name

AGENTS.md HR-5 lists `migrations/**` among the R4 paths, writable "only
when the ticket names them". T-1.15's `Build` line reads:

> a projector with durable cursors; `task_current`; shells for
> `approval_queue` and `cost_attribution`; `factory projections rebuild`;
> staleness metrics.

It does not say "migrations".

But `task_current` is a **table**, and pack `03` §2 says of the
projections:

> Columns normative, **DDL written in the owning ticket**.

And the same table names **T-1.15** as `task_current`'s owning ticket.
The `migrations/**` marking protects the pack's *existing* DDL from
silent edits; it does not forbid the ticket that owns a table from adding
it. pack `03` §2's own closing note is written for exactly this ticket:

> Every later migration that adds a table adds its own explicit GRANTs in
> the same file; default privileges are NOT used.

So `migrations/0002_projections.sql` creates `task_current` with pack
`03` §2's normative columns and grants it:

```sql
GRANT SELECT, INSERT, UPDATE ON task_current TO factory_projector;
GRANT SELECT                        ON task_current TO factory_readonly;
```

The projector **reads the log and never writes it** — it gets `SELECT` on
`events`, not `INSERT`. That is pack `03` §2's rule and it is why the
projection cannot forge history.

**The alternative was rejected:** shipping the projector against a port
with no table would have meant A0.6 could only be proven against the
in-memory double, which is a weaker proof of the same claim.

**This is a judgement call and it is the owner's to ratify or reverse.**
If the owner prefers the migration to be deferred, the change is a
single file's move to a later ticket plus the Postgres half of the
contract test skipping until it lands.

## 2. The two shell projections

pack `03` §2 assigns the projection tables to later tickets:

| Table | Owning ticket | T-1.15 ships |
|---|---|---|
| `task_current` | **T-1.15** | the table, the reducer, the cursor |
| `review_queue` | T-2.16 | the threshold table's row only |
| `approval_queue` | T-2.09 | the reducer, the cursor, the carried state |
| `cost_attribution` | T-4.05 | the reducer, the cursor, the carried state |
| `workflow_performance`, `agent_performance` | T-4.01 | the threshold table's row only |
| `calibration_*` | T-4.02, T-4.04 | the threshold table's row only |

A "shell" here is not a placeholder. `reduceApprovalQueue` is the real
reduction — it creates the row on `approval.requested` and **removes** it
on the event that answers it; `reduceCostAttribution` is the real
aggregation over the `(day, workflow, role, model)` bucket. When T-2.09
and T-4.05 write their tables, the projector's output lands in them
unchanged.

What the shells do **not** have is Postgres tables. The
`PostgresProjectionStore` holds those two projections' rows and their
carried state **in memory** and says so in its own file header. That is
the one place where the Postgres store is a weaker thing than the in-memory
one, and it is deliberate and recorded.

## 3. The one rule that makes the fold idempotent

This is the substantive design decision, and it is worth the owner's
review because A0.6 rests entirely on it.

A0.6: "every projection can be dropped and rebuilt identically". The
rebuild replays the whole log. So a reducer that **accumulates** would
double its figures on the replay — `cost_attribution` is a genuine sum,
and `task_current`'s `spent_usdMicros` looks like one too.

The rule the package follows is:

> **The projection never computes an aggregate the log does not already
> carry.** Where the log carries the figure, the projection copies it.
> Where it does not, the projection leaves the field alone.

So `task_current.spentUsdMicros` is **copied** from the event's payload
(the authoritative running total the task row carries), never summed. And
`cost_attribution` — which genuinely must sum — keeps its **contributions
map** keyed by the contributing event's **id**, and derives the totals
from the map. A replayed event **overwrites its own contribution**
instead of adding a second one.

### Why the key is the event's id and not its `seq`

The mutation harness forced this distinction into the open, and it is a
real one rather than a theoretical one:

- `seq` is the log's **position**;
- `event_id` is the event's **identity**.

A position changes when the log is **re-based** — compacted, or rebuilt
from a truncated window. An identity does not. So a bucket keyed by `seq`
counts a re-based event as a **new** contribution and doubles its totals,
while a bucket keyed by the id writes the same contribution twice and the
totals hold.

The first mutation I wrote for this — "key the contribution by `seq`" —
**survived**, because in the scenario it exercised the two keys were
equivalent. The A0.6 oracle now proves the distinction directly: it
applies the *same* event twice, at *different* sequences, into the *same*
store, and the bucket's totals must not move. Under the `seq` mutation the
totals double (100 → 200 tokens) and the oracle fails.

### The `ProjectionStore` port has no accumulate operation

The other half of the rule is structural. `ProjectionStore.commit` takes
`upserts` and `removals` — **not** "increments" — and the Postgres upsert
sets every column. There is no way for a caller to add to a row. So the
idempotence is not a property a caller has to remember; it is a property
the port cannot express otherwise.

## The carried state — why the reducer needed a second thing

A fold needs a carried state, and for `task_current` and `approval_queue`
the carried state **is** the row. For `cost_attribution` it is not: the
row holds the bucket's *totals* (the pack's columns), but the fold needs
the bucket's *contributions*.

So the effect a reducer returns carries both a `row` (what is written)
and a `state` (what the next event is folded onto), and the store holds
the states alongside the rows — written in the **same commit**, so a
restart cannot find rows without the state they were derived from.

This was found by a **silent failure**: without the carried state the
`cost_attribution` reducer folded the *row* into `reduceCostAttribution`,
`totalsOf` then summed the row's fields as if they were contributions,
and the digest threw `CanonicalJsonError: non-finite number (NaN)`. The
fix was structural, not a patch.

## The store owns the cursor — and why

The rows and the cursor must commit **together**; otherwise a crash
between "rows written" and "cursor advanced" replays the events and
duplicates them. That is checklist-02 trap-4's lesson, and it drove a
design choice that is worth naming:

> **`ProjectionStore` owns the `CursorStore`.**

The projector reads the cursor from the store's cursor store and the store
writes it, inside the same transaction. If they were two independent
objects, the position the projector reads and the position the store
writes could diverge, and the projector would loop over the same events
forever — which is exactly what happened during development, before the
ownership was made explicit.

In the Postgres store the cursor's write joins the rows' transaction by
opening the transaction **through** the cursor store
(`cursors.transaction(run)`), so the two are one transaction and not two
sequential ones. The in-memory double has the same ordering — rows, then
states, then the cursor — so it is not a weaker version of the real store.

## The contract test — I-12

AGENTS.md §4: "fakes live in the package's own `fakes` directory and must
pass the **same contract tests** as the real thing (I-12)."

`tests/unit/projections-contract.test.ts` runs **one** suite against
**two** stores: the in-memory one and the Postgres one. The suite is
written once, so a behaviour cannot be checked for the fake and forgotten
for the real store.

Two details worth noting:

- **Each test builds its own store.** The suite is written against a
  *factory*, not a single store. A test that drops the rows must not leave
  the next test a store whose rows are gone — otherwise the suite tests
  the order the tests happen to run in, and a failure points at the wrong
  cause. This was not hypothetical: the first version of the file shared
  one store and the rebuild test failed because the *previous* test had
  dropped the rows.
- **The Postgres half skips when there is no container**, using the
  repo's `it.skipIf(!running)` idiom, because the absence of a Docker
  daemon is an environment limit and not a defect in the store.

## The `LISTEN` wake-up is not implemented

pack `02` §4.18 says the projector is "woken by `LISTEN`".
`packages/eventlog` already emits `NOTIFY` on `factory_events`, so the
mechanism exists — but a `LISTEN` needs a **dedicated connection** held
open, and the ticket does not name it.

The projector **polls**. The `PostgresEventSource` reads from the cursor's
position; the wake-up is a latency optimisation, not a correctness
requirement, and the rebuild guarantee does not depend on it. It is
recorded here rather than silently omitted.

## One rule I changed after the mutation harness asked

The rebuild's `identical` verdict originally required **both** the digests
to match **and** every field-level comparison to be empty. A mutation
dropping the second clause **survived** — and the reason was that the
clause was **redundant**: the digest is over canonical JSON, so any
difference the field comparison would find the digest finds too.

The clause is harmless, but a check that can never change the outcome is
not a check. The mutation was re-aimed at what the field comparison
**uniquely** does — name *which* field of *which* row differs — and the
oracle now pins that: the rebuild's report says `state: MERGED → VERIFYING`,
not merely "these rows differ".

A second mutation was added for the same reason: a row that exists on one
side and not the other must be reported as a difference. The `<row>` field
is what carries that.

## One defect this ticket surfaced in `packages/db`

The CLI's own test file — the one that checks the command's decisions
before it touches a database — hung for **30 seconds and then timed out**
on a case where the connection string pointed at an unreachable host.

The cause was not in the CLI. `pg`'s pool **retries** a failed connection
rather than giving up, and `packages/db`'s `createDatabase` set no
`connectionTimeoutMillis`. So a client pointed at a mistyped host waited
forever.

That is a defect in the **operational surface**, not in the projections:
an operator who mistyped a database host got a hang instead of an error.

The fix is additive and backwards-compatible — `ConnectionConfig` gained
an optional `connectTimeoutMs`, defaulting to 10 seconds, and the CLI
asks for 5. `packages/db` was already in this ticket's scope (the
`task_current` table type), and no existing caller changes behaviour
other than gaining a timeout it did not have.

**This is worth the owner's attention** because it changes a shared
package's behaviour for every caller: a caller that was relying on the
pool waiting indefinitely would now get an error after ten seconds. I
judged that an improvement — a pool that never gives up turns a typo into
a hang — but it is a behavioural change to a shared package, and it is the
owner's to ratify.

## What I have NOT changed

- `packages/contracts/**` — untouched. No event type was added. The
  projector reads the registered vocabulary and the transitions are
  identified by their **payload shape** (`{from, to}`), exactly as
  `packages/state`'s `replay.ts` does it, because the vocabulary has no
  `task.stateChanged`.
- `apps/api/**` — untouched. T-1.15 is not the API's ticket, and the
  projections package exports the read functions that T-1.16's operational
  surface binds to. The API's `InspectionPort` shape already matches what
  the projections produce, so the binding is a one-liner later.
- `migrations/0001_core.sql` and `migrations/0001_grants.sql` — untouched.
  The new migration is additive.
- **The other projection tables** — T-2.09, T-2.16, T-4.01, T-4.02,
  T-4.04, T-4.05.
- **The `review_queue` reducer** — T-2.16's.

**The known environment limit** is `tests/unit/baseline.test.ts` A0.32 and
A0.33, which fail on a clean tree because the baseline tool writes to

T-1.10 and T-1.11, and this ticket touches no baseline code.

**The Postgres-backed suites skip** without a Docker daemon — the
acceptance suites, the invariants, and the Postgres half of the new
contract test. They run in CI, where the daemon exists.

## The recommendation

**Ship T-1.15 as it stands.** The fold's idempotence — the property
A0.6 actually names — is proved by the oracle *and* by a mutation that
fails without it. The two shell projections are shells in their *tables*
only; their computations are real. The migration's HR-5 tension is
recorded here rather than buried, and the owner may reverse it with a
one-file move.

The one thing I would put on the owner's desk for a decision is the
**migration**. It is the only place where T-1.15 touched a path its
`Build` line does not name, and the reasoning — pack `03` §2's "DDL
written in the owning ticket", with T-1.15 named as `task_current`'s
owner — is in this document rather than in a commit message, so it can be
checked against the pack without reading the diff.
