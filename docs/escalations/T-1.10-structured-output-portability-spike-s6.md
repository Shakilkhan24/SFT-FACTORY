## What I was doing

Building `packages/gateway` — the factory's only path to a model. The ticket's
build list ends with: *"portable structured output with Zod revalidation"*.

pack 02 §4.7 spells out the mechanism:

> *"**Structured output:** `responseFormat: json-schema` is implemented
> portably (forced single tool call whose input schema is the JSON schema) or
> with the provider's native structured outputs when available `[VERIFY]`; the
> result is always **re-validated with Zod**; one repair attempt counts as a
> retry."*

So the corpus names **two** mechanisms and marks the second one `[VERIFY]`.

native one is *available*, and what it costs.

## Why I did not implement the native path

- **HR-11:** a `[VERIFY]` fact must be confirmed from official documentation or
  a spike note. Whether each provider exposes a native JSON-schema mode is
  exactly such a fact, and it is provider-version-specific.
- **The facts are S-6's deliverable, not mine to guess.** "invalid-JSON rate"
  and "token overhead" are *measurements*. A native path implemented against
  unmeasured assumptions would not be a native path — it would be a guess with
  a request body, and the guess would be in the factory's only path to a model.
- **A wrong native path is not a harmless extra.** If the native mode is
  *unavailable* on a provider and the gateway sends it anyway, the provider
  may ignore it — and the answer then arrives as prose rather than as
  schema-shaped JSON. The Zod revalidation would catch that, but only *after*
  paying for a call whose result was never going to be valid, and after a
  repair attempt that also fails. The portable path does not have that failure
  mode: it is one mechanism that works everywhere.

## What I did instead

The **portable** path is implemented in full, and the ticket's headline
structured-output oracle is proved against it.

| The rule | Where it lives | How it is proved |
|---|---|---|
| the **forced tool call** — one tool whose input schema *is* the request's JSON schema | `packages/gateway/src/structured.ts` (`forcedToolFor`) | `tests/unit/gateway-structured-output.test.ts` |
| the forced tool is **offered last**, so the provider's own tools keep their positions | `packages/gateway/src/structured.ts` (`toolsFor`) | `tests/unit/gateway-structured-output.test.ts` |
| the answer is **re-validated with Zod** — the provider's word is not the schema's word | `packages/gateway/src/structured.ts` (`revalidate`) | `tests/unit/gateway-structured-output.test.ts` |
| **one** repair attempt counts as a retry — two attempts in total, no third | `packages/gateway/src/structured.ts` (`STRUCTURED_ATTEMPTS`), `packages/gateway/src/gateway.ts` (`#attemptStructured`) | `tests/unit/gateway-structured-output.test.ts` |
| invalid **twice** ⇒ `model.reasoning` (FI-8, blueprint 08) | `packages/gateway/src/structured.ts` (`STRUCTURED_FAILURE_CLASS`) | `tests/unit/gateway-structured-output.test.ts` |
| the schema failure carries its **trigger**, so a policy's `neverOn` is obeyed | `packages/gateway/src/structured.ts` (`SCHEMA_INVALID_TRIGGER`) | `tests/unit/gateway-structured-output.test.ts` |
| a structured request with **no schema configured** is refused, not answered unchecked | `packages/gateway/src/gateway.ts` (`#checkStructuredSchema`) | `tests/unit/gateway-structured-output.test.ts` |
| the **fake supports both mechanisms**, so an S-6-driven change has somewhere to land | `packages/gateway/src/providers/fake.ts` (`nativeStructuredOutput`) | — |

The fake adapter's `nativeStructuredOutput` flag returns the answer as
`json` on the response — the native shape — and the gateway **does not read
it today**. That is deliberate, and it is the seam: when S-6 confirms the
native path is available and worth its overhead, the change is a branch in
`#attemptStructured`, not a redesign.

Every one of those rules is also **mutation-tested**
(`tools/mutate-gateway.ts`): the Zod revalidation, the attempt count of two,
the `model.reasoning` class, the trigger, and the no-schema refusal each have
a named mutation that the suite is shown to catch.

## The gap this leaves, stated plainly

The factory can produce a schema-valid structured answer **portably** — by
forcing a tool call, on any provider that can be told to call a tool.

What it cannot yet do is use a provider's **native** JSON-schema mode. That
means:

- the **token overhead** of the portable path is unmeasured. A forced tool
  call carries the schema in the tool definition and the answer in the tool
  arguments — that is *more* tokens than a native mode, and how much more is
  S-6's measurement, not my estimate.
- the **invalid-JSON rate** of each mechanism on each provider is unknown. The
  gateway's Zod revalidation and single repair are built to *tolerate* invalid
  output; their cost is a function of the rate, and the rate is unmeasured.
- the **native path may not exist** on either provider in a form worth using.
  That is a legitimate finding, and it is the one that would most change the
  ticket's shape.

The gap is not hidden: the portable path is implemented, complete and proved;
the native path is absent, and its absence is recorded here rather than
papered over with a speculative implementation.

## Options, with consequences

**A — Run S-6 and add the native path where it is confirmed (recommended).**

The owner runs S-6 against both real providers (a throwaway script, no
production code — the checklist's spike prompt says so) and records in
`docs/spikes/S-6-structured-output-portability.md`:

- whether each provider exposes a native JSON-schema mode, with the **exact**
  request field and the documented version that introduced it;
- the **invalid-JSON rate** of each mechanism over a sample of real schemas;
- the **token overhead** of each mechanism on the same request;
- the answer to the question that decides the design: is the native path
  worth it *given* the portable path already works and is already re-validated?

The implementation is then a branch in `#attemptStructured`: read the native
`json` when the provider offered it and the policy asks for it, and keep the
forced tool call as the fallback. The revalidation, the repair count and the
`model.reasoning` outcome are already in place and do not change.

Blast radius: small, and confined to one method — **provided** the branch is
gated on a confirmed fact, so a provider that lacks the mode is not sent a
request field it does not understand.

**B — Ship the portable path alone and never add the native one.**

Acceptable, and defensible on the evidence so far: the portable path works on
every provider, is already re-validated with Zod, and its cost — while
unmeasured — is bounded by the same repair budget every other failure has.

The cost of choosing this is that the factory permanently pays the portable
path's token overhead, and never learns whether it was overpaying. That is a
real cost, and it is the kind of cost a benchmark exists to remove.

**C — Implement the native path now against the published documentation,
without the spike.**

Rejected. This is the S-2 trap with a different payload. The *shape* of a
native-mode request can be read off a provider's docs, but two of S-6's three
deliverables — the invalid-JSON rate and the token overhead — are
**measurements**, and a measurement cannot be read off a documentation page.
Worse, sending an unconfirmed field to a provider that does not support it
degrades gracefully *nowhere*: the answer arrives as prose, and the repair
attempt costs another call to produce prose again.

## Recommendation

**Option A**, and before T-1.13 (the orchestrator) depends on structured
output in anger. The gateway's structured path is now the thing every
downstream agent will call, and the first real measurement of its overhead is
the first thing the factory should know rather than assume.

**Option B** is defensible for now — nothing is blocked *by* the gap, because
the portable path satisfies the ticket's oracle in full, and the ticket's
oracle is what T-1.10 is graded on. But S-6 should be scheduled, because the
gateway is now carrying the whole factory's structured-output load on the
portable mechanism without ever having measured it.

## What I have NOT changed

- `packages/contracts/**` — untouched.
- `docs/spikes/**` — untouched; **S-6 has not been written**, because writing
  it requires the two real providers and the measurements, and no test or
  fake produces a real token overhead or a real invalid-JSON rate.
- No `[VERIFY]` fact has been guessed into the code. `packages/gateway/src/structured.ts`
  says in its own doc comment that the native mechanism is not implemented
  because S-6 has not run.
- The native path has **not** been sketched in a disabled branch. The fake
  adapter's `nativeStructuredOutput` flag is the *seam* — a fact-shaped
  interface the future implementation will satisfy — not a half-written
  implementation for someone else to "finish" without knowing it is a guess.
