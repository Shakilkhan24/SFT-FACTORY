## 1. There was no runnable `factory` binary

`apps/cli/src/index.ts` exported `main()`, and **nothing invoked it**.
No package declared a `bin`. So:

- CL-G1-12 (`factory audit chain <taskId>` exit 0) named a command
  that could not run;
- CL-G1-14 (`factory doctor` passes locally) named a command that
  could not run.

`apps/cli/src/index.ts` had been written for T-1.16 as a **module**
with a `main()` export, and the unit suites call `main()` directly.
That is a fine shape for a testable module and a useless shape for a
command.

### The fix

Three files:

- `apps/cli/src/bin.ts` — the shebang, and a **dynamic** import of
  `index.js`. The import is dynamic on purpose: a static import would
  resolve `@factory/*` before the resolver hook is installed.
- `apps/cli/src/workspace-resolver.ts` — a Node `module.registerHooks`
  resolver that maps `@factory/<name>` onto
  `packages/<name>/dist/index.js`.
- `apps/cli/package.json` — the `bin` entry.

**Why the resolver hook was needed.** The workspace packages declare
`"exports": { ".": "./src/index.ts" }` — correct for TypeScript and
Vitest, and wrong for a built artifact. Node cannot load TypeScript
from `node_modules` without a loader, and this repo's packages are
workspace links. So the binary installs a resolution hook that points
`@factory/*` at the **built** output.

**A note on the types.** `@types/node` is pinned at **22.9.0**, which
predates `module.registerHooks` (Node 24+). The runtime has it; the
types do not. The hook's shape is therefore declared locally and read
off the `node:module` namespace through `Record<string, unknown>`,
with a named error when the runtime lacks it:

> `factory: this Node has no `module.registerHooks`, so the workspace
> packages cannot be resolved. Node 24 or newer is required.`

**What the owner should know about invocation.** Until `apps/cli` is
linked onto the `PATH`, the command is:

```
node apps/cli/dist/bin.js audit chain <taskId>
node apps/cli/dist/bin.js doctor
```

The database URL variables are `FACTORY_OWNER_DATABASE_URL` and
`FACTORY_PROJECTOR_DATABASE_URL`. The roles in the pack's DDL are
`NOLOGIN` by design, so the URL's user must be a **login** role — the
dev superuser (`factory`) in the dev cluster — and the CLI `SET ROLE`s
to the role it needs. This is the pack's design, not a workaround.

## 2. `factory audit chain` reported a pass on nothing

The command verified the chain correctly, but it reported the **count**
of links checked from a field the contract does not carry, and fell
back to `0`. So:

```
chain: intact (0 links checked)
```

while the log held six events. The oracle row asks for "exit 0 on an
intact run and ≠0 on a tampered one" — and this printed a **pass** for
a run it had checked nothing in.

### The fix, and why the contract was not touched

`ChainVerification` in `@factory/contracts` is **`.strict()`**, and
HR-12 forbids changing it. The first attempt widened `verifyChain`'s
return type to carry `checked` — which broke **four** invariant
tests, because `tests/invariants/event-log.test.ts` asserts
`toEqual({ ok: true })` exactly.

The correct shape is a **separate method**:

```ts
// packages/eventlog/src/postgres-event-log.ts
public async verifyChain(aggregate): Promise<ChainVerification>   // unchanged, exact contract shape
public async verifyChainDetailed(aggregate): Promise<ChainVerification & {
  readonly checked: number; readonly reason?: string
}>
```

`verifyChainDetailed` runs the same pure `verifyChainLinks` and
additionally reports how many links it checked and why it broke. The
CLI calls the detailed one; `verifyChain` is untouched.

### The second half: an empty chain is not a pass

An aggregate with **no events** has a trivially intact chain — every
link (there are none) recomputes. So `verifyChainLinks` says `ok: true`,
which is **correct as a statement about the links** and **wrong as an
audit verdict**.

The audit's question is "was this run's history verified?", and the
answer for a run that wrote no events is **no**. So the CLI now
reports it as a failure with its own reason, distinct from a broken
chain:

```
chain: NOTHING TO VERIFY
  aggregate: task:task-with-no-events
  links:     0
  reason:    the aggregate has no events, so there was no chain to verify
```

Exit code **1**, not 0. An operator reading the output can tell "there
was nothing to verify" from "the history was tampered with" — which is
the whole point of a refusal that names its reason.

## 3. The checklist's verify commands do not match where the proofs live

Nine of the eighteen G1 rows name a path that does not exist in this
repository. The **assertions** are all proved; the **routes** are
wrong. The evidence pack records the command that was run, and the
correction, for each.

| Row | Checklist names | Actually run |
|---|---|---|
| CL-G1-01/02/03/04/06/08/09 | `pnpm test:acceptance -t "A0.N"` | the suites are in `tests/unit/`, so the acceptance filter would match **nothing** and exit 0 having asserted nothing |
| CL-G1-05 | `pnpm test:fault -t "A0.5"` | ✅ correct as written |
| CL-G1-07 | `… -t "A0.7"` | the suite **is** in `tests/acceptance/definition/` — the `…` is the only difference |
| CL-G1-10 | `pnpm test:redteam -t "AT-(4\|5\|7\|8)"` | ✅ correct in shape; the filter is a no-op because the directory contains only these four |
| CL-G1-11 | `pnpm test:invariants` | ✅ correct as written |
| CL-G1-13 | `pnpm test -t "secret-scan"` | ✅ works, but names the whole unit directory; the file-scoped form is `pnpm exec vitest run tests/unit/credentials-broker.test.ts -t "secret-scan"` |
| CL-G1-15 | `pnpm test:e2e -t "NFR-07"` | the proof is **Playwright**, not Vitest — `pnpm run test:e2e:browser` |
| CL-G1-18 | `bash reference/validate_ddl.sh` | the script is in the **pack**, not the repo root — `bash tools/run-pack-ddl-oracle.sh` runs it unmodified |

**The pattern.** The checklist was written before the suites were
filed, so the `…` in "the same script with `-t`" was a **hope** rather
than a command. Where the route was wrong, the evidence pack says so
rather than silently substituting.

**One row's scope needs naming.** CL-G1-13 says "secret scan of the
hello-task **store**". The scan proves the property on a **full fake
credential-broker run** — minted token, events, logs, artefacts and
prompts — which is where a secret actually escapes. The hello-task run
uses the **fake** provider and mints **no** credential, so scanning
*that* store would prove nothing. The property the row names is proved
at the place the secret exists; the wording does not match, and the
pack says so.

## 4. One gate row had **no oracle at all** — CL-G1-04 (A0.4)

CL-G1-04 asks: "*A0.4* two runs of the same trivial task resolve an
identical context". **No test in the repository proved it.** The only
`A0.4` in the tree was in `tests/unit/deps-rule-negative.test.ts` —
and that one is a **mislabelled** entry in the dependency-rules list
("a package importing `apps/` FAILS the deps rule"), which has nothing
to do with the context.

So the row was ticked in the pack with a citation that pointed at a
different rule's test. That is the failure mode this pack exists to
prevent, so the oracle was **built here** rather than the citation
fudged.

### The first version of the test was vacuous

The obvious way to compare two runs' contexts is to read the context
off each run's outcome. But the outcome carries the record's
**location** — `recordUri` and `recordSha256` — **not** the record.
So `expect(two.record?.context).toEqual(one.record?.context)` compares
`undefined` with `undefined`, asserts nothing, and passes against a
build whose context resolution is **random**.

The mutation harness is what proved it. The mutation *"the resolved
context digest becomes random"* **survived** the first version of the
test. That is the signal the repo's own memory records: *"a test that
asserts a constant against itself cannot notice it change."*

### The fix — read the bytes that were written

The test now reads the record **from the object store**, parses the
actual bytes, and compares the manifest **field for field** — a digest
says "these differ", and an operator needs "this field differs":

```ts
const bytes = await harness.artefacts.objectStore.get(
  `runs/${harness.options.runId}/record.json`,
);
expect(bytes).toBeDefined();
return JSON.parse(new TextDecoder().decode(bytes as Uint8Array)) as RunRecord;
```

And it carries an explicit **guard on the guard** — a test that the
record actually contains a context, so that every comparison above
cannot pass on `undefined`:

```ts
expect(record.context).toBeDefined();
expect(record.context.resolvedContextSha256).toBe(
  CONTEXT.manifest.resolvedContextSha256,
);
```

The determinism is **injected**, not hoped for: a fixed clock and a
counter id generator, so two runs differ in nothing but their own
identity. Two runs get **separate harnesses**, so they share no store —
two runs that share state are not two runs.

**The mutation now fails three of the seven tests**, and it is kept in
`tools/mutate-orchestrator.ts` so the mistake cannot come back. The
harness reports **28 caught, 0 survived, 0 vacuous**.

`tests/unit/orchestrator-a0-4-identical-context.test.ts` — 7 tests.

## 5. `tools/hello-run.ts` writes to the real event log

A new tool, outside the ticket's `Build` line. It runs the **same**
workflow the factory runs (`runHello` from `@factory/orchestrator`),
with the same fake provider, but with a `StateSink` that appends
**real** events to the Postgres event log. Without it there is nothing
for `factory audit chain` to verify, because the unit suite runs
against an in-memory log.

It is a **tool**, not a test: it is invoked explicitly, with a task id,
against a database the caller has migrated.

**It writes to the real `factory.events` table.** The run's transitions
become `task`-aggregate events, because that is what
`factory audit chain <taskId>` looks up. The tool's own docstring says
so, and it uses the **fake** provider on purpose — HR-9 forbids real
secrets here, and the nightly run is what exercises a real provider.

**The tool needs the resolver hook.** The workspace packages point
their `exports` at TypeScript source, so a bare `node tools/hello-run.ts`
dies with `ERR_MODULE_NOT_FOUND` on `packages/db/src/connection.js`.
The tool's usage line now carries the flag that fixes it:

```
FACTORY_OWNER_DATABASE_URL=postgresql://… \
  node --import ./tools/compiled-resolver.mjs ./tools/hello-run.ts <taskId>
```

This is the same gap the CLI binary hit (§1) — one gap, two tools. It
is worth the owner's attention as a **repo-wide** shape: the packages
declare a `.ts` entry, which is right for TypeScript and for Vitest,
and wrong for anything Node runs. A `package.json` `exports` map with a
`require`/`import` condition pointing at `dist` and a `types` condition
pointing at `src` would remove the need for the hook entirely. That is
a change to every package's manifest, so it is **not** this ticket's to
make; it is recorded here.

**The event types are mapped, not invented.** The event log checks
`eventType` against the **registered vocabulary** (pack `03` §5) and
rejects anything else, so the orchestrator's node transitions are
mapped onto registered node events:

```ts
const TRANSITION_EVENT_TYPES: Readonly<Record<string, string>> = {
  READY: 'node.ready',
  LEASED: 'node.leased',
  RUNNING: 'node.executionStarted',
  SUCCEEDED: 'stage.completed',
  FAILED: 'stage.failed',
  INCOMPLETE: 'stage.incomplete',
};
```

A transition with no registered event is a **gap**, not a silently
dropped fact — the tool throws with the transition named, because
"the log does not have that" and "the log lost it" are different
claims.

## 6. `factory doctor` — a new command the gate row named but no ticket built

CL-G1-14 names `factory doctor`, and no ticket in W2 asks for it. It
was built here because a gate row that names a command is a request
for that command.

Five checks, each naming itself on failure: `database`, `migrations`,
`event-log`, `hash-chain`, `schemas`. The doctor **fails closed** — an
unreachable database is a failed check, not a passed one — and it
**names the fix** ("run `factory db migrate`") rather than only the
symptom.

The checks are **not** vacuous: `tests/acceptance/cli/T1_17_doctor.test.ts`
drives them against a real Postgres and proves each one can fail — an
unreachable database, an unapplied migration (the doctor names the
file), a tampered event log (the tamper done through the owner role
with the append-only trigger disabled, as an attacker would), and an
out-of-date schema export.

## 8. The `LISTEN` wake-up is still not implemented

Carried from T-1.15. The stream polls the log at the cursor, the same
mechanism the projector uses. `LISTEN`/`NOTIFY` needs a dedicated
held-open connection and belongs to the worker's ticket.
