# ESCALATION · T-1.06 · the repo allow-list has no definition-document kind

- **Ticket:** T-1.06 — Definition store and applier (checklist 03, R4)
- **Trigger:** AGENTS.md §5 (contract change needed) and §6 (the ticket and the
  blueprint ADRs disagree about the definition's vocabulary)
- **Status:** the applier is complete and green; **this one input document cannot
  be validated**, so the repository's own definition does not validate as a
  whole.

---

## What I was doing

Building `packages/definition` and `factory definition validate | plan | apply`.
The last step of the ticket's own oracle is to run the CLI against *this
repository's* definition. It correctly refused:

```
$ factory definition validate
the definition is invalid (1 problem(s)):
  repos/software-factory.yaml: the document kind "RepoRegistryEntry" is not one the factory knows
exit: 1
```

The refusal is correct behaviour — the loader fails closed on a document kind it
does not know, which is the behaviour the ticket demands ("an invalid bundle ⇒
apply refused, the previous version stays active"). The problem is not the code.
The problem is that `definition/repos/software-factory.yaml` declares a kind the
contracts have never defined.

So the corpus is **internally inconsistent**: three places require a repo
allow-list document to exist in `/definition`, the file exists and is committed,
but no place specifies its kind or its schema. `RepoOnboarding` is a different
document and cannot absorb it.

## Why I did not just fix it

- **HR-12 / AGENTS.md §5:** `packages/contracts` is frozen; a contract change is
  its own tiny ticket (size S, R3) opened by the owner. Adding a kind to
  `DEFINITION_KINDS` is exactly that.
- **AGENTS.md §6:** "the ticket and a blueprint ADR disagree" is a
  stop-and-escalate trigger.
- **`definition/**` is R4** (`definition/criticality/software-factory.yaml`,
  and the file's own header: "R4: changing this file changes what the factory is
  allowed to touch"). Re-kinding or deleting it is an owner action, not mine.

## Options, with consequences

**A — Add a `RepoRegistryEntry` kind to the contracts (recommended).**
Owner opens a tiny `contracts` ticket (S, R3): add the kind to `DEFINITION_KINDS`,
add a strict Zod schema, add a `definition.repo-registry` entry to the schema
registry. Blast radius: `DEFINITION_KINDS` is referenced by
`DefinitionDocument` (`definitions.ts:745`) and by the definition package's
`DEFINITION_SCHEMAS` map, which is a compile-time exhaustive record — so the new
kind must be added there too, in T-1.06. No existing kind changes; no existing
document changes shape; the schema registry grows by one row. The alternative is
that the repo allow-list stays undocumented and unvalidatable forever, which is
the worse outcome: pack 04's webhook boundary ("repo ∈ definition allow-list")
has no machine-checkable source.

Because `DEFINITION_SCHEMAS` is `Record<DefinitionKind, SchemaLike>`, adding
the kind to the contracts makes the definition package **fail to compile**
until the schema is added there too. That is the desired behaviour: the
compiler, not a runtime surprise, is what stops the gap being forgotten.

**B — Give the file an existing kind.** Not possible without changing what the
document *means*: `RepoOnboarding` is the target repo's command contract, and
`CriticalityMap` is a path→tier map. Neither carries `enabled`, `selfTarget` or
`protectedPaths`. This would also delete information the factory needs.

**C — Remove the file from the definition directory.** Rejected: the file is
committed evidence for G0 and checklist 01 T-0.05, pack 04 §2.1 requires the
allow-list to be definition-driven, and dropping it would silently widen the
factory's authority boundary — the exact opposite of deny-by-default (HR-8).

## Recommendation

**Option A.** A tiny contracts ticket adding `RepoRegistryEntry` (S, R3), then
T-1.06 rebases and completes with the repository's own definition validating.

A minimal schema that fits the committed file and the pack's needs:

```
kind: RepoRegistryEntry
spec:
  repo: string
  defaultBranch: string
  enabled: boolean (default true)
  selfTarget: boolean (default false)
  criticalityRef: string?          # path under /definition
  onboardingRef: string?            # path in the target repo
  protectedPaths: string[]          # policy-level path deny
```

`protectedPaths` belongs here because pack 03 §4.7's `protectedPaths` and the
policy rule `deny-agent-protected-paths` (`when: { action: repo.write, actorKind:
agent, pathsMatch: "@protectedPaths" }`) need a *source*; today that source
exists only in this unvalidatable file.

## What I have NOT changed

- `packages/contracts/**` — untouched.
- `definition/repos/software-factory.yaml` — untouched (R4).
- `definition/**` — untouched.
- No kind has been invented inside `@factory/definition` to paper over the gap;
  `DEFINITION_SCHEMAS` stays an exhaustive map over the contracts' kinds, so
  the moment the contracts gain the kind the loader accepts it and no other
  change is needed.
