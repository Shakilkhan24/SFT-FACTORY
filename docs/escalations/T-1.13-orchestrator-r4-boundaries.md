# T-1.13 · Orchestrator — the R4 boundaries and the three ports that ship empty

**Status:** open, for the owner
**Ticket:** T-1.13 · Orchestrator · W2 · L · R3
**Date:** 2026-11-11

## The short version

T-1.13 builds `packages/orchestrator` — the stage runner, the executor
registry, the execution loop, resume, cancel, budgets, failure classes and
escalation. It ships green: 147 unit tests across nine files, and a mutation
harness with 27 mutations, all caught.

Three things the ticket names are **not** in this ticket's scope, and I have
recorded them here rather than silently dropping them:

1. **The Postgres run store** — `migrations/**` is R4 and the ticket does
   not name it, so the run store ships as a **port** with an in-memory
   double.
2. **The production `harness` adapter** — the T2 sandbox is T-2.x, so the
   `harness` executor ships as a **port** with a fake.
3. **The production `human` approval wait** — the approval access point is
   T-1.14's, so the `human` executor ships as a **port** with no
   implementation.

Nothing else was dropped. In particular, **no contract was edited** —
`packages/contracts/**` is R4 and untouched, and the ticket needed no
change there (see below).

## Why no contract change was needed

This is worth stating because it is unusual: T-1.13 is an R3 ticket that
would normally be expected to add vocabulary. It did not, because **the
contracts already own every word the orchestrator needs**:

| The orchestrator needs | The contracts already have it |
|---|---|
| the 14 stage kinds, and the 12 v1 implements | `STAGE_KINDS`, `V1_STAGE_KINDS` |
| the 4 executor kinds | `ExecutorKind` |
| the 10 failure classes | `FailureClass`, `FAILURE_CLASSES` |
| the escalation triggers | `ESCALATION_TRIGGERS` |
| the task state machine's guards | `TASK_GUARDS`, `isTerminal` |
| a stage's declared executor and isolation | `WorkflowStage.executor`, `.isolation` |

So `packages/orchestrator/src/runtime/stage-kinds.ts` *reads* `V1_STAGE_KINDS`
rather than re-declaring the twelve, and `failures.ts` keys its retry table
off `FailureClass`. The contract is the source of truth, not a copy of it.
HR-12 is satisfied by construction rather than by argument.

This also means **no new event type was needed**. The events the orchestrator
would emit — `node.ready`, `node.executionStarted`, `stage.completed`,
`stage.failed`, `stage.incomplete`, `tool.denied`, `policy.denied`,
`environment.provisioned`, `environment.cleaned`, `budget.exhausted` — are
all in the registered vocabulary. The orchestrator does not emit them yet
(the emission is wired to the event log in T-1.14's access point and
T-1.15's projections), but it does not need a *new* one to do so.

## The three ports that ship empty

The ticket names four executor kinds. Two of them have no production
implementation in v1, and the ticket does not ask for one.

### 1. The `harness` executor — the T2 sandbox is T-2.x

ADR-0017 says the harness is for "the **Worker**, and Workflow-D / C fixers
only", and — the load-bearing sentence — "the boundary is a policy that must
be enforced at the definition level, not a type — a misconfigured workflow
could try to use `harness` for a Reviewer unless the registry checks it."

So the **registry** is what enforces it, and it does:

- a `harness` executor is refused for any stage kind outside
  `HARNESS_ELIGIBLE_STAGE_KINDS` (`implement`), with the refusal naming the
  ADR;
- an unimplemented stage kind (`deploy`, `investigate`) is refused with the
  kind named;
- a stage kind with no executor registered is refused — **not** downgraded to
  `deterministic`.

That last one follows blueprint `13` §2.3: "Deny by default and escalate.
'Let the orchestrator try and see' is not available anywhere in the system."
A silent fallback would be the opposite of that.

What ships is the `HarnessAdapter` **port** (`run`, `kill`) and a fake. The
T2 container work is T-2.x's.

### 2. The `human` executor — the approval wait is T-1.14's

ADR-0024 (notifications and approvals) owns the approval wait, and the
access point through which a human approves is **T-1.14's** ticket. So
`human` is a declared executor kind with no implementation behind it yet.

This is a deliberate hole and it is *visible*: `resolveExecutorKind('approve')`
returns `{ok: true, executor: 'human'}`, and the registry then **refuses**
to resolve it because no executor is registered for `human`. The refusal is
a refusal with a reason, not a silent skip.

### 3. The Postgres run store — `migrations/**` is R4

`migrations/0001_core.sql` already has a `runs` table, but the ticket does
not name `migrations/**` and HR-5 marks it R4, so I did not write a
migration. The run store ships as a `RunStore` **port**:

- `start(run)` — records the run;
- `finish(runId, patch)` — commits the result;
- `runsFor(taskId, nodeId)` — the runs of a node;
- `liveRuns(taskId)` — the runs that have started and not finished.

with an `InMemoryRunStore` double.

**The double implements the semantics, not just the calls.** This matters,
because A0.5's second proof depends on it: the first committed result wins.
`finish` on a run that has already finished returns `{applied: false,
winnerRunId}` and does not overwrite; `start` on a finished run does not
resurrect it. That is pack `02` §4.8's rule, and it is the rule the
"idempotent node handler" proof is about.

**The mutation harness found a real bug here.** Before T-1.13, the fake's
`start` overwrote the record with `status: 'running'`, so a duplicated
handler call resurrected a finished run and the second result was applied.
The A0.5 oracle caught it. That is the sixth time in this repo that a
mutation harness has found a defect a green suite did not — and the first
time it found one in the **double** rather than in the production code.

## The Postgres consequence for the resume path

The resume path's job is "rebuild in-flight state from the DB". With an
in-memory double, "the DB" is the store the process is holding. That is
enough to prove the *logic* — a `RUNNING` task with no live run becomes
`ESCALATED(resume_failed)`, an expired lease is re-queued exactly once — and
not enough to prove the *durability*.

**A crash of the process loses the run store.** In production the store is
Postgres, and the resume path would then rebuild from the `runs` table. The
logic is written against the port precisely so that swapping the double for
the Postgres implementation is a wiring change and not a rewrite.

**This is a gap, not a blocker.** But it should not be forgotten: until the
Postgres run store lands, "resume after a control-plane crash" is proven
against an in-memory store, and the crash-recovery path has never been
exercised across a process boundary.

## One rule I changed after the mutation harness asked

The runner's cleanup reclaims the environment, then the credentials. A
failure in one must not skip the other — a leaked credential is worse than a
leaked directory.

I first wrote it so that a failed credential reclamation **throws** when the
environment reclamation succeeded, and is **swallowed** when both failed. The
mutation harness pointed out why that is backwards: the mutation that
inverted the condition **survived**, which meant the suite could not tell
the two behaviours apart. But the deeper problem was the behaviour itself —
it made the *worst* case the quietest one. A run that leaked both a
directory and a credential is the run an operator most needs to hear about.

So the rule is now: **a failed credential revocation always throws.** The
environment's failure is recorded and the credential reclamation is still
attempted; the credential's failure is never silent, whether or not the
environment also failed. Two tests now cover it — one for the single
failure, one for the double failure.

## What I have NOT changed

- `migrations/**` — untouched. No table was added.
- `packages/contracts/**` — untouched. No event type was added, and
  `packages/contracts/events.md` was not edited.
- **The `packages/orchestrator/package.json` dependency list** — untouched.
  The plan for this ticket named `@factory/policy`, `@factory/gateway` and
  `@factory/isolation` as additions; the delivered implementation turned out
  to need **none** of them, because every decision the orchestrator makes is
  a pure function of `contracts`-owned vocabulary. The package's existing
  dependencies were sufficient.
- **The `human` and `harness` implementations** — T-1.14 and T-2.x.
- **The Postgres run store** — a later ticket, as above.

## The recommendation

**Ship T-1.13 as it stands.** The three empty ports are empty for stated
reasons (R4 boundaries and later tickets), each gap is visible as a refusal
with a reason rather than a silent skip, and no contract or migration was
touched.

The one thing I would put on the owner's desk for a decision is the
**Postgres run store**, because it is the only gap that weakens a stated
proof rather than deferring an implementation: until it lands, the
"resume after a control-plane crash" proof has never been exercised across a
process boundary. If the owner wants that proof to be real before the
checklist closes, the run store needs a migration and a Postgres
implementation — which is R4 work, and R4 work is not mine to schedule.
