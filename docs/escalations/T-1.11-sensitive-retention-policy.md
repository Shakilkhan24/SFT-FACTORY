# ESCALATION · T-1.11 · the `sensitive` retention class has no period in the corpus

- **Ticket:** T-1.11 — Run-artefact store and redaction (checklist 03, R3/M)
- **Trigger:** AGENTS.md §6 — *"an external fact differs from the ticket/spike"*;
  the ticket says *"Retention classes per `15 §2.5`"*, and blueprint 15 §2.5's
  `sensitive` row names a policy that is not in the corpus
- **Status:** the artefacts package is complete and green. All **six**
  retention classes are implemented. `sensitive` carries a conservative
  **30-day** default, and the caller may supply the policy's period.

---

## What the corpus says

blueprint 15 §2.5 gives the six classes and their retention:

| Class | Retention |
|---|---|
| `engineering` | 12 months |
| `security-relevant` | 24 months |
| `incident` | 24 months |
| `evaluation` | Until the set is retired |
| `sensitive` | **Per the data classification policy** |
| `debug` | 30 days |

Two of the six name something that is **not a duration**:

- `evaluation` — *"until the set is retired"* is an **event**, not a period.
  A retirement is not a number of months, so the expiry is the **caller's**
  to supply, and the class has **no default period**.
- `sensitive` — *"per the data classification policy"*. The policy is
  **not in the corpus**. I searched the whole pack, the blueprint reference
  and the checklists: the phrase appears in exactly one place, blueprint
  15 §2.5's table row. There is no document that states the policy's period.

## Why `sensitive` got a 30-day default and `evaluation` got none

The two look similar and behave differently, deliberately.

**`evaluation` has no default at all.** Its retention is *"until the set is
retired"* — a retirement is something that **happens**, and the factory
knows when. Guessing a duration for it would mean inventing a period the
corpus explicitly declined to state, and the consequence of guessing wrong is
that a replay set's artefacts are deleted before the set is retired — which
would destroy the very thing the set exists to replay.

**`sensitive` has a 30-day default.** Its retention is *"per the data
classification policy"* — a policy that *would* state a duration, but is
absent. When the policy is absent, the failure modes are not symmetric:

- a record kept when it should have gone is a **privacy failure** — the
  factory held personal or regulated data for longer than anyone sanctioned;
- a record that went early is a **cost** — and, for `sensitive`, an
  operational problem, not a breach.

So the default errs towards **deleting**. Thirty days is the same period
blueprint 15 §2.5 gives `debug`, and it is deliberately conservative.

## Why this is an escalation and not a ticket-blocking gap

The class is **fully supported**. A caller who knows the policy's period
passes it:

```ts
const expiry = expiryFor('sensitive', completedAt, { months: 12 });
await store.finalise(parts, index, 'sensitive', expiry);
```

and the class is honoured end to end — the row's `retention_class` says
`sensitive`, the row's `retain_until` says the date the policy's period
produced, and the purge job selects it exactly like any other class.

Nothing is blocked *by* the gap. What is blocked is **correctness of the
default**: the 30-day figure is a **safe substitute**, not the policy's
answer, and the factory should not be running with it in production.

## Options, with consequences

**A — Publish the data classification policy and set the period (recommended).**

The owner writes the policy — a short document stating, per data class, the
retention period for a run artefact touching it — and the period becomes the
`sensitive` default rather than a substitute. The change to the code is one
line in `DEFAULT_PERIODS`.

Blast radius: one line of behaviour, plus the policy document. The class,
the plumbing and the purge are already in place.

**B — Keep the 30-day default and require every `sensitive` run to pass its expiry.**

The class stays supported, but the default is never relied upon: the caller
always supplies the period. This is safe but pushes the work onto every
caller, and a caller that forgets gets 30 days — silently, because the
default exists.

**C — Treat `sensitive` like `evaluation`: no default, refuse without an expiry.**

The most conservative option, and the one that most loudly refuses to guess.
But it changes the shape of the class: a run classified `sensitive` becomes
un-finalisable without an explicit policy input, which is a **behavioural
break** for any caller that classified a run `sensitive` and expected it to
work.

## Recommendation

**Option A**, before the factory handles a run that genuinely touches
personal or regulated data.

Until then the 30-day default is the right failure mode: it errs towards
deleting rather than towards keeping, and it is the same period `debug`
gets, so the class is treated as *short-lived* rather than *long-retained*
until the policy says otherwise.

**Option C** is the one I would choose if the policy were unlikely to
arrive soon — it makes the absence loud instead of silent. But the policy is
a corpus gap that should be filled rather than encoded, and the ticket's
own wording ("Retention classes per `15 §2.5`") says the period was always
*meant* to come from outside the code.
