# ESCALATION · T-1.08 · the MCP server registration has no definition-document kind

- **Ticket:** T-1.08 — Capability registry and ToolBroker (checklist 03, R4)
- **Trigger:** AGENTS.md §5 (contract change needed) and §6 (the ticket and the
  blueprint disagree about the definition's vocabulary)
- **Status:** the broker is complete and green; **the MCP server's
  configuration has no machine-readable source**, so it stays in code.

---

## What I was doing

Building `packages/broker` — the registry, the ten-step pipeline, the five
adapters, the MCP client port, and the invocation stores.

The MCP adapter needs to know **which server to talk to**: its transport
(command, or URL), its trust level, its credential reference, its egress
policy, and which capabilities it is allowed to contribute. blueprint 11 §3.2
specifies exactly that document, and gives it a kind:

```yaml
apiVersion: factory/v1
kind: McpServerRegistration
metadata:
  id: mcp.vcs.internal
  owner: platform-vcs
transport:
  type: stdio
  command: ["mcp-server-vcs"]
  version: "1.4"
trust:
  level: internal            # internal | external | untrusted
  verified: true
scope:
  allowedCapabilities: ["git.*"]
  deniedCapabilities: ["git.forcePush"]
credentials:
  credentialRef: cred.vcs.bot
network:
  egress: none
health:
  checkType: spawn-and-list
  intervalSeconds: 60
discovery:
  mode: registered-static
  reconciledAt: "2026-11-01T09:00:00Z"
```

The contracts have no such kind. `DEFINITION_KINDS`
(`packages/contracts/src/definitions.ts:31`) has twelve entries and
`McpServerRegistration` is not one of them.

## Evidence

| Fact | Source |
|---|---|
| The blueprint specifies the document and its kind | blueprint 11 §3.2 "The MCP server registry" — the YAML above; §3.1's "MCP is **not** the registry … MCP servers are *sources* that the registry reconciles with" |
| The kind is **not** in the contracts | `packages/contracts/src/definitions.ts:31–44` — `DEFINITION_KINDS` has 12 entries; `McpServerRegistration` is not among them |
| The kind is **not** in the schema registry | `packages/contracts/src/schema-registry.ts` — one row per kind, sourced to pack 03 §4.1–§4.11; there is no `definition.mcp-server` |
| The pack's definition kinds do not carry it | pack 03 §4 "Definition document kinds" defines §4.1–§4.11 only. There is no §4.12, so the twelve kinds in `DEFINITION_KINDS` are exactly the pack's. |
| The blueprint itself calls the document a *definition* document | the YAML block's first line is `apiVersion: factory/v1` and its second is `kind: McpServerRegistration` — the same two-line identity block every definition document carries |
| The template that introduces it says so | `software-factory-pack/.../templates/MCP_INTEGRATION.md:1` — "Template — Integration Registration (`McpServerRegistration` / `ToolCapability`)" |
| The trust level is **load-bearing** | blueprint 11 §3.2's trust table: `untrusted` ⇒ "**Never offered to an agent**"; `external` ⇒ "each tool must be individually approved before it may be offered" |

The trust level is the sharp edge. It is the difference between a tool that
may be offered to an agent and one that may never be. If the level lives only
in code, the rule that depends on it is enforced only by whoever writes the
code — and the factory's whole claim is that the rules are *declarative* and
*checkable*.

## Why I did not just fix it

- **HR-12 / AGENTS.md §5:** `packages/contracts` is frozen; a contract change is
  its own tiny ticket (size S, R3) opened by the owner. Adding a kind to
  `DEFINITION_KINDS` is exactly that.
- **AGENTS.md §6:** "the ticket and a blueprint ADR disagree" is a
  stop-and-escalate trigger. Here the *blueprint* has a document the *pack's*
  definition kinds do not cover.
- **HR-5:** the ticket's named paths are the broker's. Inventing a definition
  kind inside `@factory/broker` would be a contract change wearing a
  different hat.

## What I did instead

The MCP server's configuration is **in code**, in the broker's own module:

- `packages/broker/src/mcp/client.ts` — the `McpClient` **port**: the seam
  the adapter talks through. A second implementation (the official MCP SDK)
  is a later change, and it implements this port rather than replacing it.
- `packages/broker/src/mcp/in-process-client.ts` — the in-process client,
  used by the fixture server.
- `packages/broker/src/mcp/fixture-server.ts` — a JSON-RPC server that
  advertises one registered tool and one **unregistered** tool, so the
  reconciliation rule can be proved in both directions.

The **reconciliation rule** — the part that is load-bearing — is implemented
and proved *now*, in `packages/broker/src/registry.ts` and
`tests/unit/broker-mcp-reconciliation.test.ts`:

- a tool an MCP server advertises that the registry does not list **does not
  exist** (blueprint 11 §3.2);
- a registered tool the server no longer advertises is marked `unavailable`;
- the discrepancy is recorded as a **reconciliation finding**, not an event.

What is missing is only the *source* of the server's own configuration —
where the trust level and the credential reference are declared, so the
registration can be **definition-driven** rather than code-driven.

## Options, with consequences

**A — Add an `McpServerRegistration` kind to the contracts (recommended).**
Owner opens a tiny `contracts` ticket (S, R3): add the kind to
`DEFINITION_KINDS`, add a strict Zod schema matching blueprint 11 §3.2, add a
`definition.mcp-server` row to the schema registry.

Blast radius: as with the open `T-1.06` escalation, `DEFINITION_SCHEMAS` in
`packages/definition` is a compile-time exhaustive record over the contracts'
kinds — so the new kind makes that package **fail to compile** until the
schema is added there too. That is the desired behaviour: the compiler, not
a runtime surprise, is what stops the gap being forgotten. The broker's MCP
configuration then moves from `packages/broker/src/mcp/` into
`definition/mcp/*.yaml`, and the broker reads it.

**B — Reuse `ToolCapability` for the server registration.** Rejected: they
are different documents. A `ToolCapability` is one *capability* with an
effect class, a scope and a trust tag; an `McpServerRegistration` is one
*server* with a transport, a trust level, a credential reference and an
egress policy. blueprint 11 §3.2's trust table (`internal` / `external` /
`untrusted`) is about the **server**, while `ToolCapability.trust` is about
one capability's input and output. Conflating them would put a server-level
trust decision in a per-capability field.

**C — Leave it in code, permanently.** Acceptable as a temporary state, and
it is what this ticket ships. The cost is that the trust level — the rule
that says an `untrusted` server's tools are *never* offered to an agent — is
enforced by the code that happens to be there, and is not part of the
factory's *declarative* surface. It is also not visible to
`factory definition validate`, so a misconfigured server cannot be caught by
validating the definition.

## Recommendation

**Option A**, alongside the open `T-1.06` escalation — the two are the same
kind of gap and can be closed by one contracts ticket if the owner prefers
(S, R3 → M).

A minimal schema that fits blueprint 11 §3.2:

```
kind: McpServerRegistration
spec:
  transport:
    type: stdio | http
    command: string[]?           # stdio
    url: string?                 # http
    version: string
  trust:
    level: internal | external | untrusted
    verified: boolean
    signature: string?
  scope:
    allowedCapabilities: string[]
    deniedCapabilities: string[]
  credentials:
    credentialRef: string
  network:
    egress: none | allowlist
  health:
    checkType: string
    intervalSeconds: int
  discovery:
    mode: registered-static | probed-and-diffed
    reconciledAt: datetime?
```

## What I have NOT changed

- `packages/contracts/**` — untouched.
- `definition/**` — untouched (R4).
- No definition kind has been invented inside `@factory/broker` to paper over
  the gap; the MCP configuration stays where the ticket put it, in code, and
  is named as such in the broker's module documentation.
- The **reconciliation rule** — the load-bearing part — is implemented and
  proved, and does not depend on this gap being closed.
